# Working on Filenewer

## Project overview

Filenewer is a Laravel application offering online file conversion and processing tools, a tool directory, blog posts, content pages, and contact forms. The public interface uses server-rendered Blade templates; Filament provides the administration interface at `/admin`.

Use the implementation, `composer.lock`, and `package-lock.json` as the source of truth. The README contains older examples: the registration view is `auth/signup.blade.php`, the main directory view is `tools/index.blade.php`, and the configured build tool is Vite 7.

Read `CLAUDE.md` for the existing Laravel Boost conventions. Relevant development skill instructions are available in `.claude/skills/` for Pest, Livewire, and Tailwind work. Use Boost tools for version-specific documentation when available; do not assume that a configured MCP server is connected in every session.

## Stack

- Laravel 12; Composer declares PHP `^8.2`. Check the lock file's requirements for the complete installed dependency set, including development tools, before selecting a PHP runtime.
- Filament 5 with Livewire for administration; public pages primarily use Blade and plain JavaScript.
- Tailwind CSS 4, its typography plugin, Vite 7, and the Laravel Vite plugin.
- Laravel Socialite for Google, GitHub, and Facebook OAuth.
- Spatie Sluggable and Sitemap; Dompdf, Laravel Excel, and PhpSpreadsheet are declared PHP dependencies.
- Pest 4 for tests and Laravel Pint for PHP formatting.

## Important application flows

- `/` and `/tools` use `ToolController::index()`. Categories are eager loaded with active tools ordered by `order`; `?category=<slug>` filters the category query.
- `/tools/{slug}` loads an active database tool and related tools. It renders `tools.<slug>` when that view exists, otherwise `tools.show`. A Blade file alone does not make a tool available through this route: the corresponding active database record is required.
- Tools belong to categories; blogs relate to tools through `blog_tool`. Tool and page slugs use Spatie Sluggable and are not regenerated on updates.
- Signup posts to `signup.store`. It accepts `first_name`, `last_name`, `email`, `password`, and accepted `terms`; the two name fields become `users.name`. Preserve agreement between the controller's password rules and the form's hints/strength meter.
- OAuth configuration lives in `config/services.php`. Keep credentials in local environment configuration and out of source control.
- Admin access is governed by `User::canAccessPanel()`, with different behavior in production and development. Preserve this authorization boundary when changing authentication.
- Tool processing varies by page. For example, the PDF-to-Word Blade page calls `https://api.filenewer.com/api/tools/pdf-to-word`, while local `/pdf-to-word/*` routes also exist. Inspect a page's JavaScript and request/response contract before changing its backend assumptions. The external API implementation is not present in this repository.

## Local setup and commands

Run commands from the repository root. Use the existing lock files to install dependencies.

```text
composer install
npm ci
```

For a fresh checkout, copy `.env.example` to `.env` only if `.env` does not already exist (PowerShell: `Copy-Item .env.example .env`). Configure the intended local database, then run:

```text
php artisan key:generate --no-interaction
php artisan migrate --no-interaction
npm run build
composer run dev
```

Generate an application key only during initial setup. `composer run dev` starts the Laravel server, queue listener, and Vite together. Alternatively, run `php artisan serve` and `npm run dev` in separate terminals.

`composer run setup` also exists, but it generates an application key and runs migrations with `--force`; inspect its effects before using it on an existing environment. `DatabaseSeeder` creates a test user and does not invoke `ToolSeeder`. To populate a local tool catalog, inspect `ToolSeeder` before explicitly running `php artisan db:seed --class=ToolSeeder --no-interaction` against the intended local database.

The local PDF conversion controller requires `soffice` (LibreOffice) on the process PATH, and `ocrmypdf` for optional OCR. It writes temporary files under `storage/app/conversions/` and stores download metadata in the session. Installing PHP or npm dependencies does not install those programs.

## Change conventions

- Follow sibling files and the existing directory structure. Keep changes focused; do not add dependencies or perform unrelated refactors without authorization.
- Use Laravel generators for new framework classes, with `--no-interaction`. Prefer typed PHP parameters/returns, braces for control structures, and Eloquent relationships with eager loading.
- For new validation work, follow the Form Request guidance in `CLAUDE.md`; existing controllers currently also contain inline validation.
- Use `config()` in application code; read environment variables through configuration files. Prefer named routes for internal links.
- Extend `layouts.base` and use its `content` section. SEO primarily comes from variables such as `$title`, `$description`, and `$canonicalUrl`, rather than a title section. Preserve structured data and shared tool components.
- The layout exposes `schema`, `scripts`, and `styles` stacks in the head and `footer` at the end of the body. Put DOM-dependent scripts in the footer stack or initialize them after the DOM is ready.
- Reuse the `fn-*` theme colors, DM Sans/DM Mono fonts, and existing responsive styling. Tailwind configuration lives in CSS; do not introduce a legacy Tailwind configuration file for routine changes.
- Keep form CSRF tokens, validation feedback, escaped output, upload checks, and authorization intact. Treat filenames, conversion formats, and download paths as untrusted input.
- Use UTF-8, LF line endings, and four-space indentation as specified in `.editorconfig`.
- Never commit secrets, uploaded files, generated conversions, or edits to `vendor/`, `node_modules/`, or generated caches/build artifacts unless the task explicitly calls for them. Preserve unrelated local changes.

## Verification and known pitfalls

- Public language switching posts to `locale.update` and saves a validated locale in the session. `SetLocale` runs after session middleware. Supported languages and HTML language/direction metadata are defined in `config/app.php`; `default_locale` preserves the configured default independently of the request's current locale.
- Laravel Lang (`laravel-lang/common`) supplies framework translations. Published files live under `lang/` for `en`, `ar`, `fr`, `es`, `hi`, and `zh_CN`. Use `php artisan lang:update --no-interaction` to refresh framework translations; preserve custom JSON entries. Wrap new public copy in `__()` and add translations to all six JSON catalogs. Use `trans_choice()` for counts and `Illuminate\Support\Js::from()` when embedding translated strings in JavaScript.
- Arabic uses RTL. Prefer logical Tailwind utilities (`ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`) for shared layouts. Keep email addresses and code in LTR direction. Public tool names and titles look up JSON translations of their source text; descriptions and FAQ strings normalize whitespace before catalog lookup. Unknown external API messages retain their original language.
- Tools, categories, blogs, and pages declare their translatable fields in `TRANSLATABLE_CONTENT`. Nullable JSON `<field>_translations` columns store language overrides; original columns remain the English defaults. `HasContentTranslations::localized()` resolves the selected language, configured fallback language, and original content. Plain text retains catalog fallback; rich HTML uses saved content without translating markup. Tool `localizedDescription()` and `localizedBody()` remain available. Tool tags accept arrays or legacy comma-separated strings; use `sourceTags()` for badges/filters and `localized('tags')` for display/metadata. Keep slugs, foreign keys, filenames, images, icons, dates, order, and publication flags outside translation maps. Admin forms use `TranslationTabs`; `ContentTranslationsTest` and `ToolContentTranslationsTest` cover public rendering, defaults, allowed columns, and admin persistence.
- Translation hooks alone do not supply translated values. Add actual entries to all six catalogs for visible copy, including placeholders, labels from PHP loops, SEO text, and JavaScript feedback. The login password placeholder has explicit regression checks for every supported language. The localization suite also compiles all public Blade templates to catch syntax errors from translation expressions.
- Tool details translate PHP loop labels, placeholders, options, FAQs, client-side progress/errors, dynamic controls, and result summaries. Use `ToolMessages::html()` only for trusted interface snippets, not uploaded HTML or authored articles. Keep form values, selectors, file formats, and API parameters independent of translated labels. Embed translated JavaScript strings with `Js::from()`; dynamic `:valueN` replacements must avoid prefix collisions such as `:value1` and `:value10`.
- Verify localization with `php artisan test --compact tests/Feature/LocalizationTest.php tests/Feature/LocalizedPagesTest.php tests/Feature/ToolDetailLocalizationTest.php tests/Feature/ToolContentTranslationsTest.php tests/Feature/ContentTranslationsTest.php`. The detail suite checks explicit catalog coverage using `tests/Fixtures/tool-detail-translation-keys.json`, dynamic placeholder preservation, trusted HTML message escaping, and every detail template in all five added languages. It compares control identifiers and radio/select values against English to catch changes to tool contracts. Add new interface keys to the catalogs and the audited fixture.

- Run relevant Pest tests for behavior changes: `php artisan test --compact`, or `php artisan test --compact --filter=<name>`. `composer run test` clears configuration before running the suite.
- `phpunit.xml` uses SQLite `:memory:`, array cache/session/mail, and a synchronous queue. `RefreshDatabase` is currently commented out in `tests/Pest.php`; database-backed feature tests need schema setup, typically by opting into that trait.
- Localization tests cover switching, validation, fallback, translation catalogs, and database-backed public pages. The starter homepage test in `tests/Feature/ExampleTest.php` still lacks database setup and fails on missing categories tables when run against the configured in-memory SQLite database. These tests do not validate external conversion behavior.
- Run `php vendor/bin/pint --dirty` for PHP changes, and `npm run build` for frontend changes. For UI work, check affected pages at mobile and desktop widths and exercise validation and tool interactions.
- Documentation-only changes need content/path verification, not application tests or a frontend build.
- `routes/web.php` currently assigns the name `home` to both `/` and `/home`. Check redirects and route caching when working on those routes.
- `/convert` references `ExcelToPdfController`, which is absent from `app/Http/Controllers/`. Inspect this before relying on that endpoint or route inspection commands that resolve controller classes.
- Some tool views contain incomplete request targets (for example, `csv-to-json` uses `fetch('')`). A rendered interface does not establish that processing works. Verify each changed tool's actual endpoint and error/download handling.
- The forgot-password controller currently renders a page; `routes/web.php` does not define the complete password-reset submission/token flow.
- Report the checks actually run and any environment limitations. Do not fix unrelated known issues as part of a narrow task.
